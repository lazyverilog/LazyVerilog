# Review, September 2026: start-up indexing, edit latency, and a bug hunt

Two questions, measured rather than reasoned about:

1. where the remaining headroom is in **cold project indexing** and in **`didChange`
   latency** — the two costs a user actually feels;
2. what breaks when the server is driven from a real editor with awkward input.

Nothing here is implemented.  Every claim is a measurement with the recipe next to
it, and the findings are ranked by what they are worth.

## Test bench

| | |
|---|---|
| Host | 4-core VM, 15 GB RAM, Linux 6.18, page cache warm |
| Build | `Release`, commit `a5c0b1c` |
| Corpus `rtl1k` | 953 filelist entries from CVA6 + Ibex RTL → 1154 shards, 774 modules |
| Edit-path files | real `csr_regfile.sv` (3 089 lines) plus generated RTL at 17 770 and 57 890 lines |

`rtl1k` is built by pointing a `lazyverilog.toml` at a `.f` listing
`tests/rtl/cva6` and `tests/rtl/ibex` (`+incdir+` for each directory holding a
`.svh`).  It is not OpenTitan-sized, but it is real RTL with real headers, and
every number below is reproducible from it.

Two conventions from `docs/dev/startup-perf.md` are kept: four numbers rather than
one (wall at full CPU, wall at one CPU, user CPU, maxRSS), and **min** as the
honest column on a shared runner.

# Part 1-1 — Initial indexing

## The numbers

`tools/startup_bench.py`, 5 runs per cell, median (min–max):

| mode | 1 CPU | 2 CPU | 4 CPU | user CPU | maxRSS |
|---|---|---|---|---|---|
| `--no-cache` | 831.6 ms (771–853) | 421.4 ms (410–432) | **347.1 ms** (335–355) | 0.80 s | 124–151 MB |
| cold (builds the cache) | 841.0 ms (742–853) | — | 355.3 ms (340–406) | 0.90 s | 158 MB |
| `--warm` | **99.8 ms** (93–127) | 114.5 ms (99–122) | 128.7 ms (109–129) | 0.07–0.10 s | 85 MB |

Shard and module counts are identical in every row (1154 / 774), so nothing in
the table is a change in how much work was done.

Round 9's win is intact and large: 347 ms → 100 ms, 831 ms → 100 ms on one core.
Two things in that table are not what you would want, though.

## S1 — The warm path is single-threaded, and extra cores make it *slower*

Read the warm row left to right.  **99.8 → 114.5 → 128.7 ms as cores go 1 → 2 → 4.**
The mins move the same way (93.3 → 99.1 → 109.2), so it is not noise in one cell:
three configurations, five runs each, monotone in both statistics.

This is the single largest remaining start-up cost, because after the first
launch *every* launch is a warm launch.

`gdb`-sampled stacks during a warm run (40 samples, all threads), non-idle frames
only:

```
 13  Analyzer::preload_cached_shards(unsigned long) const
 11  IndexCache::load(std::string_view) const
  9  (anonymous namespace)::read_regular_file(std::filesystem::path const&)
  3  deserialize_index_shard(std::string_view)
  2  std::filesystem::status(...)
```

against

```
 56  Analyzer::background_index_loop() const      <- every one of these is in
 40  condition_variable_any::wait(unique_lock&)      a condvar wait
```

So: one thread does the whole warm start inside `preload_cached_shards()`
(`src/analyzer.cpp:6431`), and every other background worker sleeps through it on
the cache-preload gate (`src/analyzer.cpp:7484`).  That gate is correct in intent —
a worker that starts parsing a file the preload was about to satisfy has already
spent what the cache exists to save — but it serialises the whole of the warm
path, not just the decision.

The work being serialised is per-file and embarrassingly parallel:

* `cache->load(uri)` reads and deserialises one shard — **22 MB** across the corpus;
* `still_valid()` → `digest_of()` reads and hashes the source file and each of its
  `include`s — **7.4 MB** more;
* `resolve_include()` re-runs slang's header search, memoised.

~30 MB of read-and-hash in ~100 ms on one thread, with three cores parked.  There
is no shared mutable state in the loop body: hits are accumulated into a local
`std::vector<Hit>` and only installed under `map_mutex_` at the end
(`src/analyzer.cpp:6626`).  The two memo maps (`incdir_resolution`,
`local_resolution`) and the digest memo are the only cross-file state.

**Why more cores makes it worse.**  The extra threads do no work, but they are
woken by every `background_cv_.notify_all()` and go back to sleep; and
`shard_writes_need_inline_drain()` turns the dedicated cache-writer thread *on*
when `available_cpu_count() > 1` (`src/analyzer.cpp:6178`), so the prune sweep the
preload queues (`src/analyzer.cpp:6619`) becomes a cross-thread handoff plus a
drain barrier instead of an inline call.  On a warm start there is nothing else
for that thread to overlap with.

Note `read_regular_file()` (`src/index_cache.cpp:673`) builds each shard through
`std::string(std::istreambuf_iterator<char>(in), ...)` — an `ifstream` growing a
`std::string` a buffer at a time.  For 22 MB of shards that is a lot of avoidable
copying next to a `read()` into a sized buffer, or an `mmap`.

For reference, the project's own published numbers show the same shape at
OpenTitan scale and rule out "it is just a small corpus": PERF.md round 10 lists
opentitan warm at **836 ms on all CPUs against 835 ms on one**, and round 9 lists
uvmproj warm at 280–306 ms against 291–298 ms.  Zero parallel speedup, twice,
on corpora 4x and 8x larger than this one.

**Worth:** the warm path is ~100 ms of almost entirely parallelisable I/O and
hashing on a 1154-shard project, and is the cost of every launch after the first.

## S2 — A cold launch has no index at all until the queue drains

Already listed as open in PERF.md round 9, and this measurement is what it costs
today: on a 953-file project the first launch answers cross-file questions with
nothing for **347 ms** at full CPU and **831 ms** on a constrained slice.  There
is exactly one `ProjectIndexSnapshot` publish per burst, requested only once the
queue empties (`background_index_loop()`, `src/analyzer.cpp:7449`).

clangd's `BackgroundIndex` takes the other route: its `BackgroundIndexRebuilder`
is a `SwapIndex` updated *during* indexing, so symbols become queryable as shards
land rather than at the end.  The shard cache removed this problem for every
launch after the first; it did not remove it for the first, or for the launch
after a config change, which re-queues everything.

## S3 — On real RTL, building the index costs more than parsing it

This is the finding most likely to redirect future work, because the existing
rounds are all framed around parse and preprocess cost.

`gdb`-sampled stacks over a cold uncached run, 4 CPUs, 284 whole-thread stacks,
classified by what the stack is actually inside:

| bucket | stacks | share of *busy* |
|---|---|---|
| `SyntaxIndex::build` → `collect_combined_occurrences` | 46 | 41% |
| slang parse / preprocess | 36 | 32% |
| `build_header_shards` | 13 | 12% |
| `SyntaxIndex::build` (rest) | 11 | 10% |
| everything else | 5 | 5% |
| — idle background workers | 70 | — |
| — idle main / cache writer | 93 | — |

`SyntaxIndex::build` is **51% of the work**, against 32% for slang.  The
occurrence collector is the hot half of it, and its leaf frames say why:

```
6  collect_combined_occurrences(...)::{lambda(Token const&, string, RefForm)#1}::operator()
4  SourceManager::getRawLineNumber<std::shared_lock<std::shared_mutex>>(SourceLocation, ...)
4  SourceFileIdResolver::for_location(...)
4  __pthread_rwlock_rdlock_full64
4  __pthread_rwlock_rdunlock
3  SourceManager::getColumnNumber(SourceLocation) const
```

Every reference occurrence asks slang's `SourceManager` for a line and a UTF-16
column (`token_pos_line1_col0()`, `src/syntax_index_shared.cpp:288` and `:715`),
and each of those takes slang's `shared_mutex` and binary-searches the buffer's
line table.  The read-write lock shows up in the profile in its own right.  A
per-buffer line table built once per file — the folding path already has
`LineTable` — would answer the same questions without the lock and without the
search.

The other half of the cost is what is stored: `add_reference_entry()`
(`src/syntax_index_shared.cpp:718`) pushes a `ReferenceEntry` carrying **two heap
strings** per occurrence, `name` and `symbol_debug`, and `symbol_debug` is a
canonical id like `module_signal::cpu::clk` that repeats across thousands of
entries.  The on-disk format already interns these through a string table,
"because an OpenTitan shard set holds 2.3M reference entries drawn from far fewer
distinct names" (`src/index_cache.cpp:136`) — but the in-memory representation
does not, which is the likeliest single cause of the 895 MB maxRSS PERF.md round
10 reports for opentitan.

## S4 — 2.4x on 4 cores: the tail, not a serial section

No-cache scaling is 831.6 → 421.4 → 347.1 ms for 1 → 2 → 4 CPUs: **2.40x on four
cores, 60% efficiency**.  It does not fit Amdahl (a two-point fit from the 1- and
2-CPU cells predicts 216 ms at 4 CPUs against 347 ms measured), which points at
tail imbalance rather than a fixed serial region — consistent with the profile
above, where 70 of 284 stacks are background workers idle while work is still
outstanding, and with the FIFO queue `startup-perf.md` already flags ("a handful
of generated `*_reg_top.sv` files are a large share of total time, so FIFO
scheduling can strand one worker while others idle").

Sorting the queue longest-file-first is the standard fix and needs only a `stat`
per entry, which the preload already does.

## Ranking, part 1-1

| | finding | why it is worth doing |
|---|---|---|
| 1 | **S1** parallelise the shard preload | every launch after the first; ~100 ms serial on 1154 shards, and it *regresses* with cores today |
| 2 | **S3** line/column without `SourceManager`, intern `symbol_debug` | 51% of cold-start work and the dominant memory term |
| 3 | **S2** publish the snapshot incrementally | 347–831 ms of no answers on a first launch or after a config change |
| 4 | **S4** longest-file-first queue | ~40% of the 4-core parallel budget |

# Part 1-2 — `didChange` latency

## The numbers

`tools/edit_latency_bench.py`, 20 keystrokes, client-observed round trip:

| file | lines | `foldingRange` | `inlayHint` | `didChange`→diag |
|---|---|---|---|---|
| `csr_regfile.sv` (real) | 3 089 | 3.4 ms | 6.2 ms | 3.0 ms |
| generated | 17 770 | 38.9 ms | 19.1 ms | 10.7 ms |
| generated | 17 770 (1 CPU) | 49.8 ms | 19.6 ms | 18.8 ms |
| generated | 57 890 | **274.1 ms** | 65.4 ms | 37.7 ms |

On ordinary RTL the edit loop is in good shape.  On a large file `foldingRange`
is the whole problem, and it is the one request the editor issues from the
`didChange` notification itself, on the single thread that answers everything.

## E1 — `foldingRange` is super-linear in fold count, not in file size

First, the cost is not the payload and not the lex.  Requesting the *same*
snapshot repeatedly hits the per-snapshot fold cache, which isolates
serialisation from computation:

```
57 890-line file: 22 543 ranges, 1 943 KiB on the wire
  first request on a snapshot   264.5 ms      <- compute
  repeats on the same snapshot  5.3, 5.3, 5.2 ms   <- copy + JSON only
```

So ~98% is computation.  Second, a file of the *same* size with almost no folds
is cheap:

| file | bytes | lines | ranges | compute |
|---|---|---|---|---|
| `flat57k.sv` (flat declarations) | 1.64 MB | 57 889 | 2 | 40–56 ms |
| `big42k.sv` (nested if/case) | 1.46 MB | 57 890 | 22 543 | 264 ms |

The *larger* file is 5x cheaper.  ~45 ms is the lex-and-line-table floor; the
rest tracks fold count.

Measured in-process on the repo's own scaling corpus (`folding_scaling_source()`),
with the cache defeated — see E2:

| folds | ms | vs previous |
|---|---|---|
| 3 121 | 7.49 | — |
| 6 241 | 18.87 | 2.52x |
| 12 481 | 55.51 | 2.94x |
| 24 961 | 154.07 | 2.78x |
| 49 921 | **903.24** | **5.86x** |

Linear is 2.0 per doubling.  This is 2.5–2.9 in the middle and **5.86 at the top**,
an overall exponent of 1.73 across the 16x range.  `docs/dev/edit-perf.md` states
"clangd's lex-only implementation is quadratic in practice … ours is not"; on this
evidence ours is super-linear too, and worse than clangd's quoted 3.5–3.9 once the
file is large enough.  The candidates are in `normalize_folds()`
(`src/features/folding_range.cpp:992`), which makes six passes over the fold list,
allocates a fresh vector in most of them, sorts on a tuple containing the
`std::string kind`, and keys two hash maps on that same string.

Worth noting for context: clangd folds only bracket pairs, `#if` regions and
comments, so on an equivalent file it produces far fewer ranges to begin with —
its fold count is not a per-construct count.  LazyVerilog's 22 543 ranges for
57 890 lines is one fold every 2.5 lines.

## E2 — The `[folding][scaling]` guard has measured nothing since `2897673`

This is the finding to act on first, because it is what would have caught E1.

`fastest_folding_ms()` (`tests/test_folding_ranges.cpp:1229`) calls
`provide_folding_range()` N times **on one `Analyzer` and one document**, then
takes `samples.front()` after a sort — the **minimum**.  Commit `2897673`
("perf(folding): compute a snapshot's folds once, not once per request") added
`DocumentState::folding_ranges_`, so runs 2…N are cache hits.  The minimum of
{one computation, N−1 cache hits} is a cache hit.  The guard measures the cost of
copying a `std::vector<FoldingRange>`.

As shipped:

```
[folding scaling] stages=240 folds=3121 ms=0.00867  stages=480 folds=6241 ms=0.016871 ratio=1.94591
```

8.67 **microseconds** for 3 121 folds.  With a fresh `Analyzer` per run (the only
change):

```
[folding scaling] stages=240 folds=3121 ms=7.20507  stages=480 folds=6241 ms=17.9713 ratio=2.49427
```

**831x.**  The ratio it reports today is the ratio of two vector copies, which is
linear by construction and can never fail the `< 3.0` check, whatever folding
does.  This is precisely the failure mode `docs/dev/indexing.md` warns about for
the shard cache — "a warm test has to distinguish a hit from a reparse" — arriving
in the folding tests instead.

The technique that is now wrong is min-of-N, which was correct when it was written
(`ec95b5d`): every call recomputed.  A fresh snapshot per run, or a
median/first-sample, restores it.  Extending it past ~12 k folds would also make
it catch the 5.86x knee.

## E3 — The same folds are computed twice per keystroke

`didChange` produces **two** `DocumentState` objects with identical text: the
text-only placeholder installed by `enqueue_parse()` (`src/analyzer.cpp:1011`) and
the parsed one installed by `parse_worker_loop()` (`src/analyzer.cpp:1153`).  The
fold cache lives on `DocumentState`, and neither the placeholder nor the parsed
state inherits its predecessor's folds — `enqueue_parse()` carries
`include_dependencies` and `previous_parsed` forward but not `folding_ranges_`.

A fold request that lands in the reparse window and another that lands after the
commit therefore both pay full price for byte-identical text:

```
trial 0: in-reparse-window 352.8 ms | after parse commit (same text) 253.9 ms | repeat 4.9 ms
trial 1: in-reparse-window 269.2 ms | after parse commit (same text) 248.5 ms | repeat 4.5 ms
trial 2: in-reparse-window 254.9 ms | after parse commit (same text) 264.6 ms | repeat 5.2 ms
```

The second column is the bug: the text did not change, and the answer is
provably identical, but the cache went with the old snapshot.  Carrying
`folding_ranges_` forward when the new state's text compares equal is a two-line
change that halves the worst case.

## E4 — Head-of-line blocking is measurable, and it is what the user feels

`RemoteEndPoint(..., max_workers = 1)` (`src/server.cpp:481`) serialises every
request from every file.  On the 57 890-line file:

```
completion alone                            100.6 ms
completion queued behind one foldingRange   447.0 ms   (fold answered at 335.7 ms)
```

The completion the user is waiting on takes **4.4x longer** because a request
they never asked for is in front of it.  `edit-perf.md` names this hazard; this is
the number.

clangd's `TUScheduler` runs **per-file worker threads** (`AsyncThreadsCount`), so
one file's expensive request cannot delay another file's, and read-only actions
run against an immutable AST/preamble snapshot.  LazyVerilog's `DocumentState` is
already an immutable snapshot and `provide_folding_range()` already touches
nothing but `state->text` — so folding in particular is thread-safe to answer off
the dispatch thread today.

## E5 — `$/cancelRequest` is ignored

```
fold#60 answered at 262.0 ms
fold#61 cancelled 10 ms after it was sent -> answered at 586.0 ms, error = None
```

The server computed and returned the cancelled request in full.  There is no
cancellation path on the folding/inlay-hint handlers, and no `RequestCancelled`
error is ever produced.

`edit_watermark_` (`src/server.cpp:1376`) is a good approximation of the same
idea, but it only fires when a *newer `didChange` for the same URI* has already
been read off the transport.  It does nothing for an explicit client cancel, for a
superseded request on a different file, or for a client that cancels on cursor
movement.

clangd has both halves: `Cancellation.h` gives `isCancelled()` and a
`CancelledError` mapping to `operation_canceled`, and `TUScheduler` adds
`ASTActionInvalidation::InvalidateOnUpdate`, described in its own header as *"The
request will be implicitly cancelled by a subsequent update(). Useful for requests
that are generated by clients, without any explicit user action."*  That sentence
describes `foldingRange` and `inlayHint` exactly.

## E6 — Smaller items on the same path

* **Three copies of the fold vector per reply.**  `provide_folding_range()` returns
  `*folds` by value from a `shared_ptr` it just cached
  (`src/features/folding_range.cpp:1297`); the handler wraps that in *another*
  `shared_ptr` and then copies it again into `rsp.result`
  (`src/server.cpp:1383–1387`).  For 22 543 ranges each holding a `std::string
  kind` that is three full deep copies.  Measured at ~5 ms of a 264 ms request —
  small, but free to remove.
* **`didChange` copies the whole buffer on the dispatch thread.**
  `std::string text = state->text` (`src/server.cpp:1190`) copies the file, and
  `lsp_offset_pair()` then walks from byte 0 to the edited line
  (`src/server.cpp:191`).  On a 1.5 MB buffer edited near the end that is a copy
  plus a full scan per keystroke, ahead of everything else in the queue.
* **The first `inlayHint` on a new snapshot builds the structural index inline.**
  62 ms on `big42k.sv`, 112 ms on `flat57k.sv`, then ~1 ms for repeats on the same
  snapshot — and it returned **0 hints** in both cases, so that is the cost of
  discovering there is nothing to say.
* **`[folding].enable = false` does not make the handler cheap.**  The
  `inlayHint` handler early-returns on `config_.inlay_hint.enable`
  (`src/server.cpp:1432`); the folding handler has no equivalent check.  Since
  Neovim 0.12.5 advertises `foldingRange.dynamicRegistration = false`, a config
  reload cannot unregister it, so a user who turns folding off mid-session keeps
  paying the full cost for the rest of the session.  Verified: after
  `[folding].enable = false` + `didChangeConfiguration`, `foldingRange` still
  returned 3 ranges.

## Ranking, part 1-2

| | finding | why it is worth doing |
|---|---|---|
| 1 | **E2** repair the scaling guard | it is the only thing standing between folding and a silent quadratic regression, and it is inert |
| 2 | **E1** de-super-linearise `normalize_folds()` | 274 ms/keystroke at 57 k lines, 903 ms at 50 k folds |
| 3 | **E3** carry the fold cache across the parse commit | halves the worst case, ~2 lines |
| 4 | **E4** answer `foldingRange` off the dispatch thread | completion 447 ms → ~100 ms behind a fold request |
| 5 | **E5** honour `$/cancelRequest` | correctness as well as latency; see B2/B3 |
| 6 | **E6** the four small ones | cheap, independent |

# Part 2 — Bug hunt

Driven from headless Neovim 0.12.5 against `build/lazyverilog-lsp`, plus a raw
JSON-RPC client for things a well-behaved client will not send.  Formatting was
out of scope.  Harnesses are reproduced at the end.

## B1 — `foldingRange` character offsets are byte counts, not UTF-16 units

`LineTable::first_non_space_column()` and `LineTable::line_length()`
(`src/features/folding_range.cpp:52` and `:60`) return byte offsets, and `emit()`
(`:82`) writes them straight into `FoldingRange::startCharacter` /
`endCharacter`.  LSP requires positions in the negotiated `positionEncoding`,
which is UTF-16 by default — and every other position the server emits goes
through `utf16_column()`.

Measured, on a file whose fold ends on `  end // 中文のコメント`:

```
fold 0..4 kind=region startChar=0 endChar=9  | endline bytes=9  utf16=9
fold 1..3 kind=region startChar=2 endChar=30 | endline bytes=30 utf16=16   <- byte count
```

`endCharacter = 30` on a line that is 16 UTF-16 units long: past the end of the
line.  Neovim sends `lineFoldingOnly = true` and ignores both fields, which is why
this has never shown up; a client that honours them gets an out-of-range column
whenever a fold's first or last line contains any non-ASCII text — CJK comments
being the obvious case.

**Severity:** low impact today, trivially wrong, and it will bite the first client
that does character-precise folding.

## B2 — A request that fails to deserialise gets no response at all

Any request whose params fail to parse is logged to stderr and **dropped**.  No
result, no error, nothing:

```
id=10  textDocument/definition          answered=NO  <-- never answered
id=11  textDocument/definition          answered=NO  <-- never answered
id=12  textDocument/hover               answered=NO  <-- never answered
id=13  textDocument/foldingRange        answered=YES
id=14  textDocument/completion          answered=NO  <-- never answered
id=15  textDocument/references          answered=NO  <-- never answered
id=16  textDocument/foldingRange        answered=YES
```

stderr carries `Reason:Exception when process requestnotification message: unsigned`
— the `Reflect` reader for `lsPosition` rejects a negative integer, the exception
unwinds out of `RemoteEndPoint::dispatch`, and the id is forgotten.

The trigger used here is `position.character = -5` / `line = -1`.  That is
malformed, but it is reachable: some clients send `-1` for "unknown", and any
client bug or protocol-version mismatch produces the same shape.  JSON-RPC
requires a response for every request that carries an `id`; without one the
client's pending-request table leaks that entry permanently, and
`vim.lsp.buf_request_sync` blocks until its own timeout.  The server itself stays
healthy — later requests are answered normally — so this is a client-side leak,
not a hang.

**Fix shape:** catch at the dispatch boundary and reply `InvalidParams` with the
id, rather than letting the exception discard it.

## B3 — `$/cancelRequest` is not implemented

See E5.  A cancelled request is computed in full and returned as a normal result.
A conforming server should reply `RequestCancelled` (`-32800`), and with
`max_workers = 1` and a 274 ms `foldingRange` in the queue there is real latency
riding on it.

## B4 — The folding scaling guard is inert

See E2.  Filed as a bug as well as a perf finding, because CI currently reports a
passing guard over a measurement that is 831x off.

## B5 — `lua/lazyverilog/config.lua` has a duplicated block

`inlay_hints` and `folding` each appear twice in `M.defaults`, with their comment
blocks, at lines 33/43 and 52/62 — a 20-line paste duplicated verbatim.  Lua takes
the last assignment, so behaviour is unaffected; the file is 78 lines and 20 of
them are a copy.

## What did not break

Worth recording, because negative results are evidence too.  Everything below was
attacked deliberately and behaved correctly.

**Shard cache.**  This is in very good shape.

| scenario | result |
|---|---|
| cold → warm, unchanged project | identical symbols, shards reused |
| source file edited between launches | invalidated, re-indexed |
| shared header edited between launches | invalidated, includers re-indexed |
| header created that satisfies an existing `` `include `` for the first time | resolution moves, old symbols gone (round 10 holds) |
| header shadowed by an earlier `+incdir+`, then unshadowed | correct in both directions |
| same spelling resolving locally in one dir and via `+incdir+` in another | both correct; creating a local header moves only that file |
| file deleted + dropped from the filelist | shard swept, symbols gone |
| `define` changed in `lazyverilog.toml` | `` `ifdef `` branch flips correctly |
| every shard truncated to 7 bytes | miss, reparse, correct results |
| every shard overwritten with random bytes | miss, reparse, correct results |
| valid header + bit-flipped body | miss, reparse, correct results |
| shard path replaced by a directory | miss, reparse, correct results |
| `.cache/lazyverilog/index` replaced by a regular file | miss, reparse, correct results |
| 10x `SIGKILL` mid-index, then a clean launch | 300/300 shards, **0 temporary leftovers**, correct results |
| three servers launched concurrently on one empty cache | all three correct, 3 shards, 4th launch reads them fine |
| read-only project root | correct results, no crash |
| `[index].cache = false` | correct results, no `.cache` directory created |
| unsaved buffer edit, then restart | unsaved symbol correctly absent from the cache |
| unsaved **header** edit, then restart | unsaved symbol correctly absent; includers unpoisoned |

**`foldingRange` corner cases** — all in-bounds, non-inverted, no crash:
empty file; a lone newline; no trailing newline; CRLF; unterminated block comment;
unterminated `begin`; unterminated string literal; a NUL byte; UTF-8 identifiers
and escaped identifiers; nested `` `ifdef ``/`` `else ``; stray `endmodule` before
any module; 200-deep `if/begin` nesting; a single 220 KB line.

**Protocol robustness** — answered, no crash, server stayed healthy:
never-opened URI; non-`file:` scheme; empty URI; a directory URI; inverted
`inlayHint` range; `endLine = 2e9`; position past EOF; `documentSymbol` on an
unopened file; empty `workspace/symbol` query; `didChange` for a document that was
never opened; a `didChange` whose version goes backwards (correctly dropped as
stale); a request after `didClose`.

**Live folding** — 801 ranges settled, folds survive a six-keystroke burst
(801, 802, 802, 802, 802, 802), all post-burst ranges in bounds, and a full-buffer
replacement with a 2-line file correctly collapses to 1 range.  Neovim applied a
fold level to 2002 of 2002 lines after open.
